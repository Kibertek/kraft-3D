# План: оформление заказов на сайте и синхронизация с KRAFT 3D Manager

## Цель

Сделать сайт KRAFT 3D дополнительным каналом приёма заказов. Заказы с сайта должны попадать в KRAFT 3D Manager без ручного переноса данных. Архитектура проектируется с учётом будущего перехода на серверную базу PostgreSQL и доступа с нескольких компьютеров.

## Предполагаемый сценарий клиента

1. Клиент выбирает тип заказа: 3D-печать, 3D-моделирование, изготовление детали или другой доступный вид услуги.
2. Заполняет контактные данные и описание задачи.
3. При необходимости указывает параметры изделия и прикладывает файлы модели/эскиза.
4. Проверяет заявку и отправляет её.
5. Получает номер заказа и сообщение, что заявка принята. Это не обещает автоматическую окончательную цену или срок: они подтверждаются после проверки файлов и требований.

## Данные заказа

Минимальный состав:
- уникальный идентификатор заказа, создаваемый сервером;
- источник: `website`;
- дата и время создания;
- имя клиента и предпочитаемый способ связи;
- контактные данные, необходимые для ответа;
- вид услуги;
- описание задачи и пожелания;
- параметры изделия, если применимо;
- список прикреплённых файлов с именем, типом, размером и защищённым местом хранения;
- предварительная оценка стоимости, если расчёт доступен, с явным признаком «предварительно»;
- статус заказа и история изменений;
- внутренний комментарий для менеджера.

Не собирать лишние персональные данные. Не хранить файлы заказов в публичной папке сайта.

## Передача в KRAFT 3D Manager

- Сайт отправляет заказ на серверный API по HTTPS.
- Сервер проверяет входные данные, размер и тип файлов, создаёт заказ и возвращает номер.
- Менеджер получает новые заказы через авторизованный API и показывает их в списке входящих заказов.
- При импорте сохраняется исходный идентификатор сайта, чтобы повторная синхронизация не создавала дубликаты (идемпотентность).
- Заказ можно принять в работу, запросить уточнение, изменить статус, подтвердить стоимость и закрыть.
- Статусы и согласованные обновления возвращаются на сайт, когда клиентский кабинет/страница отслеживания будет реализована.

## Начальные статусы

- Новая заявка
- Требует уточнения
- Ожидает подтверждения стоимости
- Подтверждён
- В работе
- Готов
- Выдан / отправлен
- Отменён

Список должен настраиваться в менеджере позднее.

## Безопасность и надёжность

- Не подключать браузер напрямую к базе данных.
- Использовать API на сервере, HTTPS и авторизацию между менеджером и сервером.
- Секреты и ключи API хранить только в серверных переменных окружения, не в React-коде и не в Git.
- Ограничить типы и размер файлов, генерировать безопасные имена и проверять содержимое.
- Защитить форму от спама и повторной отправки.
- Записывать журнал приёма и синхронизации, обрабатывать временное отсутствие сети и повторять запросы безопасно.
- Настроить резервное копирование базы и файлов заказов.
- Хранить клиентские данные только столько, сколько необходимо для работы и соблюдения применимых требований.

## Этапы реализации

1. **Контракт данных:** согласовать поля заказа и соответствующие сущности в KRAFT 3D Manager.
2. **Форма на сайте:** сделать удобную адаптивную форму, проверку полей, загрузку файлов и экран подтверждения.
3. **Серверный API:** создать заказ, безопасно сохранить вложения, назначить номер и записать журнал.
4. **Входящие заказы в менеджере:** добавить канал «Сайт», импорт без дубликатов, просмотр файлов и контактов.
5. **Двусторонняя синхронизация:** статусы, согласованная стоимость и сообщения клиенту.
6. **Проверка:** протестировать плохие/слишком большие файлы, повторную отправку, отсутствие сети, восстановление из резервной копии и работу двух компьютеров.

## Важное архитектурное решение

Поскольку KRAFT 3D Manager планируется перевести с локальной SQLite на PostgreSQL и использовать с нескольких компьютеров, сайт и программа должны обмениваться заказами через общий серверный API. Нельзя привязывать сайт к файлу SQLite на одном компьютере. Это позволит позже менять хостинг и внутреннюю реализацию, не переделывая форму заказа.
